# 四岗位职责与维护权限

本文件定义第一版岗位模型；具体项目的已确认分工优先。冲突需明确解决，不静默覆盖项目规则。

| 岗位 | 专业职责 | 主要维护内容 |
|---|---|---|
| 技术负责人 | App、后端、接口、技术验证和发布准备；受影响的旧客户端兼容验证 | 业务代码、技术说明、接口约定、技术验证及部署记录 |
| 美学设计师 | 界面、视觉、交互设计 | 设计规范、预览、当前确认稿及设计决策 |
| 法务 | 法律文件、隐私授权、商店审核合规 | 适用协议、审查结论和法律版本关系 |
| 数据分析师 | 数据分析、指标、SQL 与数据库 | 数据定义、分析报告、数据库基线、迁移和执行证据 |

技术与数据的交界：技术维护业务 API 和应用的数据访问实现；数据分析师维护结构、SQL 与数据语义。接口或结构变化跨双方时共同确认契约与兼容性，不互相覆盖代码或 SQL。其他工具或应用的开发归属由项目明确约定，不从岗位名称自动推定。

## 三类维护权限

1. **领域专属**：相关人员可读、可提出问题；专业内容由维护方修改。跨域代写需要用户明确授权，不能仅凭工具可用就接管。
2. **共享维护**：README 登记、CHANGELOG、统一验收记录，各方只更新自己负责或有充分依据的部分。写入前重读目标段落，保留其他人的增量；发生同一区块并行修改，明确本轮写入方或隔离修改后合并，不整份覆盖。
3. **冻结记录**：已发布法律原文、已执行 SQL 等按项目约定保持不变。纠错用新的版本或补充记录，并保留替代关系，不机械搬迁。

用户授权的边界独立于岗位：发布生产、执行数据库写入、修改冻结材料、变更职责或访问权限，不能从岗位身份推导授权。例行已授权工作不重复请示。

## 跨领域牵头

优先采用用户指定的牵头方。未指定时，接单 Session 可以在原任务授权内整理依赖、推进自己的部分并提出协作请求；不能由此宣称获得其他会话的调度权。必要的角色分歧或重大取舍由用户裁决，不新增常驻管理层。
